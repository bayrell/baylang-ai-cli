# Техническая спецификация доработки проекта **BayLang AI**

> **Версия документа:** 1.0  
> **Дата:** 2025-08-13  
> **Статус:** Черновик на согласование  
> **Область работ:** добавление модуля `main` (точка входа) и обновление модуля `ai.py`

---

## 1. Обзор текущего состояния проекта

Проект **BayLang AI** — это ранняя каркасная (skeleton) реализация библиотеки для построения AI-агентов. В репозитории на данный момент присутствуют только три содержательных файла: файл `LICENSE` с лицензионным текстом, почти пустой `README.md`, содержащий единую строку `# BayLang AI`, и модуль `src/ai.py`, который описывает базовые абстракции библиотеки — сообщения, контекст, провайдеры LLM, инструменты и агента.

Критически важно понимать, что **текущий `src/ai.py` не может быть импортирован и исполнен в его нынешнем виде**, поскольку содержит сразу несколько синтаксических ошибок, делающих невозможным даже разбор файла интерпретатором Python. Помимо синтаксиса, в модуле присутствуют ошибки логики, опечатки в именах методов, нарушения инкапсуляции и полное отсутствие обработки ошибок. То есть проект находится на стадии «идея, набросанная набело», и доработка представляет собой не точечное исправление, а **существенную переработку с сохранением заявленной архитектуры**.

Папка `docs/` в репозитории на момент начала работ была пустой, поэтому данный документ становится первым техническим артефактом проекта и задаёт вектор дальнейшей разработке.

## 2. Цели и задачи доработки

**Главная цель** — превратить набросок в рабочий, тестируемый и расширяемый пакет Python-библиотеки, способный отправлять запросы в LLM через провайдера OpenRouter, поддерживать диалоговый контекст и запускаться из командной строки через новый модуль `main`.

### 2.1. Конкретные задачи

1. **Полная переработка `src/ai.py`**: устранить все синтаксические и логические ошибки, привести именование методов к единому стилю (snake_case), ввести типизацию и docstring-и, корректно выстроить иерархию наследования между классами `Provider` и `OpenRouterProvider`.
2. **Добавление модуля `main`**: создать файл `src/main.py` (и при необходимости `src/__main__.py`), который предоставляет интерактивный чат-режим и одноразовый режим запроса, читает конфигурацию из переменных окружения и аргументов командной строки, корректно завершает работу по сигналу пользователя (команды `exit`, `quit`, Ctrl+C, Ctrl+D).
3. **Нормализация протокола общения с провайдером**: текущий код отправляет некорректный набор полей (`message` вместо `messages`, `sender` вместо `role`); необходимо привести сериализацию к формату, ожидаемому OpenAI-совместимым API.
4. **Введение надёжности**: асинхронные HTTP-запросы вместо блокирующих, таймауты, повторные попытки, информативные сообщения об ошибках и логирование.
5. **Расширение подсистемы инструментов**: дополнить `ToolRegistry` и `Tool` методами регистрации, поиска и исполнения инструментов, чтобы агент мог получать вызовы инструментов (tool calling) от модели.
6. **Подготовка к тестированию**: структурировать код так, чтобы каждый класс можно было подменить тестовой реализацией (провайдер-заглушка), и добавить минимальный набор unit-тестов в будущем.

## 3. Анализ текущего модуля `ai.py`

Ниже приведён исчерпывающий перечень проблем текущего кода, сгруппированный по классам. Этот перечень служит основанием для раздела 4 и проверочным списком при приёмке работ.

### 3.1. Класс `TextMessage`

- Метод `get_data()` обращается к переменным `sender` и `message` без указания `self`, что вызывает `NameError` при выполнении; необходимо писать `self.sender` и `self.message`.
- Константы ролей (`ROLE_USER`, `ROLE_AI`, `ROLE_SYSTEM`) объявлены, но нигде не используются: провайдеру отправляется поле `sender`, тогда как OpenAI-формат требует поле `role` с допустимыми значениями `system`, `user`, `assistant`.
- Класс не проверяет корректность переданных значений, поэтому пользователь может передать `None` или пустую строку, что молча сломает запрос к API.

### 3.2. Класс `Context`

- Метод `get_data()` преобразует сообщения в словари вида `{"sender": ..., "message": ...}`, а провайдеру нужен список сообщений вида `{"role": ..., "content": ...}` — это фундаментальное расхождение протокола.
- Отсутствует метод очистки контекста, метод подсчёта количества сообщений и возможность ограничения длины диалога (обрезки старых сообщений), что критично при долгих сессиях.
- Класс не защищён от внешнего изменения списка `items` из-за публичного атрибута, что нарушает принцип инкапсуляции.

### 3.3. Базовый класс `Provider`

- Все геттеры (`get_url`, `get_model_name`, `get_api_key`) возвращают пустые строки, а класс не помечен как абстрактный — наследник может забыть переопределить какой-либо из них, и ошибка проявится только в рантайме.
- Метод `send()` объявлен как `async`, но выполняет блокирующий вызов `requests.post`, что **намертво блокирует event loop** и делает библиотеку непригодной для асинхронного использования; необходимо использовать `httpx.AsyncClient` либо `aiohttp`.
- Внутри `send()` вызывается `provider.get_url()` — обращение к несуществующей глобальной переменной `provider` вместо `self.get_url()`, что гарантированно приводит к `NameError`.
- Тело запроса формируется с ключом `"message"`, тогда как провайдеры ожидают `"messages"` (множественное число, список).
- Отсутствуют таймаут соединения, обработка сетевых ошибок и структурированное исключение для ошибок HTTP.

### 3.4. Класс `OpenRouterProvider`

- Наследование объявлено от несуществующего класса `Provder` — опечатка в имени, приводящая к `NameError` при импорте модуля.
- Конструктор объявлен как `__init__(self, api_key="", model_name="", api_key="")` с **дважды указанным параметром `api_key`**, что является синтаксической ошибкой и делает файл невыполнимым.
- Вызов родительского конструктора записан как `super()..__init__(self)` — двойная точка и лишний аргумент; правильный синтаксис: `super().__init__()`.
- Метод называется `getUrl()` вместо snake_case `get_url()`, из-за чего он **не переопределяет** родительский геттер и провайдер продолжает возвращать пустой URL.
- Адрес API указан с опечаткой: `https://openrouter.ai/v1/cjat/completions` вместо корректного `https://openrouter.ai/api/v1/chat/completions`.
- Отсутствуют заголовки, рекомендуемые OpenRouter (`HTTP-Referer`, `X-Title`), и поле `"stream"` — потоковый режим сейчас невозможен.

### 3.5. Классы `Tool` и `ToolRegistry`

- `ToolRegistry` хранит пустой список и не предоставляет методов `register`, `find_by_name` и `get_schemas` — построение списка инструментов для запроса к модели невозможно.
- `Tool` не валидирует обязательные поля `name` и `description`, а также не предоставляет JSON-схему параметров в формате, понятном моделям (Function Calling).
- Метод `execute()` возвращает `None` без каких-либо пояснений по поводу контракта результата — нужен явный контракт: инструмент возвращает сериализуемый объект или строку.

### 3.6. Класс `Agent`

- Метод `async send(self, context)` объявлен без скобок в сигнатуре — `SyntaxError`, модуль не загружается.
- Внутри `send()` вызывается `context.add_message(Context.ROLE_AI, ...)` — три ошибки сразу: константа лежит не в `Context`, а в `TextMessage`; метод `add_message` принимает один аргумент (объект сообщения), а не два; содержимое ответа модели берётся по индексу без проверки наличия ключа `choices`.
- Атрибут `self.max_iters` используется в `send_with_fallback`, но нигде не инициализируется — гарантированный `AttributeError`.
- Метод `send_with_fallback` фактически дублирует `send` в цикле, не реализуя ни резервного провайдера, ни логики остановки по ошибке — нужна явная политика fallback-цепочки.
- Несмотря на то что агенту передаётся `tools`, логика разбора tool-calls от модели и их исполнения отсутствует полностью.

## 4. Целевая архитектура модуля `ai.py` после доработки

### 4.1. Общие принципы

1. **Единый стиль именования**: все публичные методы и атрибуты — в snake_case, константы — в UPPER_CASE, классы — в CamelCase; никаких смешанных стилей вроде `getUrl`.
2. **Полная типизация**: использовать аннотации типов для всех публичных методов и атрибутов, чтобы IDE и статические анализаторы (mypy, pyright) могли проверять корректность кода на этапе разработки.
3. **Асинхронность на уровне I/O**: все сетевые операции — только через `httpx.AsyncClient`; блокирующие вызовы в асинхронном контексте запрещены.
4. **Явные исключения**: определить собственный иерархию исключений (например, `BayLangError` → `ProviderError`, `ToolError`, `ConfigurationError`), чтобы вызывающий код мог корректно различать типы сбоев.
5. **Docstring для каждого публичного класса и метода**: документация должна описывать назначение, параметры и возвращаемое значение, чтобы библиотекой можно было пользоваться без чтения исходников.

### 4.2. Класс `TextMessage`

1. **Конструктор** должен принимать `role` (одно из констант `ROLE_USER`, `ROLE_AI`, `ROLE_SYSTEM`) и `content` (непустую строку), при этом валидировать роль и выбрасывать `ValueError` при некорректном значении.
2. **Метод `get_data()`** должен возвращать словарь в формате провайдера: `{"role": self.role, "content": self.content}` — это устраняет главное расхождение протокола между контекстом и API.
3. **Статический метод-фабрика** (например, `TextMessage.user(text)`, `TextMessage.system(text)`) упростит создание сообщений в `main` и в тестах, избавив от ручного указания ролей.
4. Следует добавить `__repr__` для удобного отладочного вывода сообщений в логи.

### 4.3. Класс `Context`

1. **Внутреннее хранилище** должно быть приватным (`self._items`), а публичный доступ к списку — только через методы-итераторы (`__iter__`, `__len__`), чтобы предотвратить неконтролируемое изменение диалога извне.
2. **Метод `get_data()`** должен возвращать список словарей `{"role": ..., "content": ...}`, готовых к передаче в поле `"messages"` запроса к провайдеру.
3. **Метод `trim(max_messages)`** — отсекать старые сообщения, оставляя последние `max_messages`, что защищает от переполнения контекстного окна модели при долгих диалогах.
4. **Метод `clear()`** — полная очистка диалога для новой сессии, полезен в интерактивном режиме `main` по команде пользователя.
5. **Метод `last_response()`** — возвращать последнее сообщение роли `assistant` (или `None`), чтобы `main` мог показать ответ модели без повторного парсинга.

### 4.4. Абстрактный класс `Provider`

1. **Объявить класс абстрактным** через `abc.ABC` и пометить `get_url`, `get_model_name`, `get_api_key` и `send` декоратором `@abstractmethod` — так наследник обязан реализовать все члены, иначе создание экземпляра завершится понятной ошибкой.
2. **Метод `send(context)`** должен возвращать нормализованный результат — объект `ProviderResponse`, содержащий текст ответа, имя модели, использование токенов (если API вернул `usage`) и исходный raw-ответ для отладки.
3. **Внутри `send()`** — использовать `self.get_url()` (исправление ошибки с глобальной переменной), поле `"messages": context.get_data()`, заголовок авторизации и таймаут (по умолчанию 60 секунд).
4. **Обработка ошибок**: HTTP-статусы 4xx и 5xx должны транслироваться в `ProviderError` с кодом статуса и фрагментом тела ответа; сетевые таймауты — в отдельное понятное сообщение.
5. **Поддержка стриминга** — вынести в отдельный метод `send_stream(context)`, возвращающий асинхронный генератор чанков, чтобы `main` мог выводить ответ по мере генерации.

### 4.5. Класс `OpenRouterProvider`

1. **Исправить наследование**: класс должен наследоваться от `Provider`, все синтаксические ошибки конструктора устранены: один параметр `api_key`, один параметр `model_name`, вызов `super().__init__()`.
2. **Корректный URL**: `https://openrouter.ai/api/v1/chat/completions`, переопределение метода `get_url()` строго в snake_case.
3. **Заголовки OpenRouter**: добавить `Authorization: Bearer <key>`, `Content-Type: application/json`, а также рекомендуемые `HTTP-Referer` и `X-Title`, чтобы проект идентифицировал себя в аналитике OpenRouter.
4. **Конфигурация модели по умолчанию**: задать разумное значение по умолчанию (например, `openai/gpt-4o-mini`), чтобы `main` мог работать без обязательного указания модели.
5. **Потоковый режим**: реализовать `send_stream()` через SSE-ответ (`"stream": True`) с разбором строк вида `data: {...}` и `data: [DONE]`.

### 4.6. Классы `Tool` и `ToolRegistry`

1. **`Tool`** должен представлять собой либо абстрактный базовый класс с обязательными `name`, `description`, `parameters_schema`, либо конкретный класс-обёртка над функцией; в обоих случаях — валидация обязательных полей при создании.
2. **Метод `get_schema()`** должен возвращать схему в формате OpenAI Function Calling: `{"type": "function", "function": {"name": ..., "description": ..., "parameters": {...}}}`, чтобы список инструментов можно было передавать в запрос напрямую.
3. **`ToolRegistry`** должен提供 методы `register(tool)`, `find(name)`, `get_schemas()` и `execute(name, params)`; `register` обязан запрещать дубли имён, чтобы не было неоднозначности при вызове.
4. **`execute`** должен оборачивать вызов инструмента в try/except и превращать ошибки в `ToolError` с именем инструмента, чтобы агент мог сообщить модели о неудаче вместо падения всего диалога.

### 4.7. Класс `Agent`

1. **Конструктор** должен принимать провайдер, реестр инструментов (опционально), максимальное число итераций цикла `max_iters` (по умолчанию, например, 5) и необязательный резервный провайдер для fallback — все эти атрибуты обязаны инициализироваться.
2. **Метод `send(context)`** — исправить сигнатуру на `async def send(self, context: Context) -> str`; внутри — отправка запроса, добавление ответа в контекст через корректный API (`context.add_message(TextMessage(Role.AI, text))`), возврат текста ответа.
3. **Разбор tool-calls**: если провайдер возвращает `tool_calls` в первом сообщении ассистента, агент должен для каждого вызова найти инструмент в реестре, выполнить его и добавить в контекст сообщение роли `tool` с результатом, затем повторить запрос к модели — классический цикл ReAct.
4. **Метод `send_with_fallback(context)`** — отправка через основной провайдер; при `ProviderError` автоматический переход на резервный провайдер (если задан); при исчерпании попыток — осмысленное исключение, а не бесконечный цикл.
5. **Метод `reset()`** — очистка внутреннего состояния и контекста для новой сессии, удобно вызывать из `main` по команде пользователя.

## 5. Спецификация модуля `main` (новый файл `src/main.py`)

### 5.1. Назначение

Модуль `main` является **единой точкой входа** в приложение: он собирает конфигурацию, создаёт провайдера и агента, а затем предоставляет пользователю два режима работы — интерактивный чат и одноразовый запрос. Модуль должен быть запускаем как `python -m src.main` из корня репозитория, а также как исполняемый скрипт при наличии конструкции `if __name__ == "__main__": main()`.

### 5.2. Конфигурация

1. **Ключ API** читается из переменной окружения `OPENROUTER_API_KEY`; при его отсутствии программа должна завершиться с кодом 2 и понятным сообщением о том, какую переменную нужно задать.
2. **Модель** читается из переменной `OPENROUTER_MODEL` или аргумента `--model`; значение по умолчанию — `openai/gpt-4o-mini`.
3. **Аргументы командной строки** через стандартный `argparse`: `--prompt` (одноразовый запрос), `--model`, `--max-iters`, `--temperature`, `--no-tools`, `--verbose` (включить подробное логирование), `--version`.
4. **Приоритет значений**: аргумент командной строки имеет приоритет над переменной окружения, которая имеет приоритет над значением по умолчанию.

### 5.3. Интерактивный режим

1. При запуске без `--prompt` программа входит в цикл чтения строк со стандартного ввода, приглашая пользователя командой вида `you> `.
2. Пользовательский ввод отправляется агенту, ответ модели выводится в стандартный вывод с префиксом `assistant> `; при включённом `--verbose` дополнительно печатаются время ответа и число использованных токенов.
3. **Команды управления**: `exit`, `quit` или пустая строка с Ctrl+D — корректное завершение со статусом 0; `clear` — очистка контекста диалога; `help` — краткая справка по командам; `model <name>` — смена модели на лету.
4. **Обработка прерываний**: перехват `KeyboardInterrupt` и `EOFError` должен выводить прощальное сообщение и завершать процесс без вывода стектрейса.
5. **Логирование ошибок**: если запрос к API завершился ошибкой, в интерактивном режиме программа не должна падать — она показывает сообщение об ошибке и продолжает диалог, предлагая повторить запрос.

### 5.4. Одноразовый режим

1. При наличии аргумента `--prompt` программа выполняет ровно один запрос, выводит ответ в stdout и завершается со статусом 0 — этот режим удобен для использования в пайплайнах и скриптах.
2. Код возврата `1` означает ошибку выполнения (сбой провайдера, некорректный ответ), код `2` — ошибку конфигурации (нет ключа, неверный аргумент).

### 5.5. Структура кода модуля

1. **Функция `build_agent(args)`** — фабрика: создаёт `OpenRouterProvider`, заполняет `ToolRegistry` базовыми инструментами (например, `get_current_time`, `web_search`-заглушка), создаёт `Agent` и возвращает его; вынесена отдельно для переиспользования в тестах.
2. **Функция `run_interactive(agent, args)`** — цикл интерактивного режима, описанный в разделе 5.3.
3. **Функция `run_once(agent, prompt, args)`** — одноразовый запрос, описанный в разделе 5.4.
4. **Функция `parse_args(argv=None)`** — разбор аргументов командной строки с валидацией и значениями по умолчанию.
5. **Функция `main(argv=None)`** — оркестратор: парсинг аргументов, настройка логирования, сборка агента, выбор режима, обработка исключений и возврат кода выхода.
6. **Файл `src/__main__.py`** — тонкая обёртка, вызывающая `main()` из `src.main`, чтобы поддерживать запуск `python -m src`.

## 6. Нефункциональные требования

### 6.1. Производительность и надёжность

1. Все HTTP-запросы должны выполняться асинхронно через `httpx` с соединением и чтением по таймауту (по умолчанию 60 секунд), чтобы программа не висла при недоступном API.
2. Интерактивный режим должен устойчиво работать неограниченно долгое время: утечек памяти допускать нельзя, поэтому контекст поддерживается в памяти и ограничивается через `trim`.
3. При обрыве соединения допускается одна повторная попытка запроса перед тем, как ошибка будет показана пользователю.

### 6.2. Безопасность

1. **Ключ API никогда не должен попадать в логи и в вывод программы**; при `--verbose` вместо значения печатается только маска (первые 4 и последние 4 символа).
2. Секреты хранятся исключительно в переменных окружения; файлы конфигурации с ключами в репозиторий не добавляются.
3. Ввод пользователя передаётся в модель как есть, но служебные команды (`exit`, `clear`) обрабатываются локально и не отправляются в API.

### 6.3. Тестируемость и сопровождаемость

1. Все внешние зависимости (провайдер, реестр инструментов) внедряются через конструктор, что позволяет подставлять тестовые заглушки без мокинга сетевых вызовов.
2. Функции модуля `main` имеют чистые сигнатуры и возвращают результаты, а не печатают их напрямую — печать выполняется на верхнем уровне.
3. В проекте должен появиться `requirements.txt` (или `pyproject.toml`) с зафиксированными зависимостями: `httpx`, и, при необходимости, `pytest` для тестов.

## 8. Критерии приёмки

1. **Импорт**: `python -c "import src.ai"` завершается без ошибок — ни одной синтаксической или логической ошибки в модуле не остаётся.
2. **Запуск без конфигурации**: `python -m src.main` без переменной `OPENROUTER_API_KEY` завершается с кодом 2 и понятным сообщением, не падая стектрейсом.
3. **Одноразовый запрос**: `python -m src.main --prompt "Скажи привет"` при корректном ключе возвращает текст ответа модели и код возврата 0.
4. **Интерактивный режим**: диалог работает многократно, команда `clear` очищает контекст, `exit` корректно завершает процесс, ошибки API не роняют приложение.
5. **Серия запросов**: контекст сохраняется между репликами — модель отвечает с учётом предыдущих сообщений диалога.
6. **Инструменты**: при наличии зарегистрированного инструмента модель получает его схему в запросе, а агент корректно выполняет вызов и возвращает результат модели.
7. **Fallback**: при недоступности основного провайдера запрос автоматически выполняется через резервный, если он задан.
8. **Безопасность**: ключ API отсутствует в любом выводе программы, включая режим `--verbose`.

## 9. Риски и открытые вопросы

1. **Выбор HTTP-клиента**: спецификация рекомендует `httpx`, но если команда предпочитает `aiohttp`, достаточно заменить реализацию метода `send()` без изменения публичного интерфейса — вопрос остаётся на согласование.
2. **Реальные инструменты**: по умолчанию `main` регистрирует демонстрационные инструменты; набор боевых инструментов (поиск в интернете, работа с файлами) определяется отдельным решением и не входит в объём данной спецификации.
3. **Потоковый вывод в интерактивном режиме**: реализация SSE-стриминга в `main` является желательной, но не обязательной для приёмки первого релиза — её можно вынести во второй итерации.
4. **Версионирование API OpenRouter**: адрес и формат ответов могут меняться со стороны провайдера, поэтому все обращения к raw-полям ответа следует изолировать в одном месте класса-провайдера.

## 10. Итог

Доработка проекта **BayLang AI** сводится к двум взаимосвязанным направлениям. **Первое** — полная переработка модуля `src/ai.py`: устранение всех синтаксических и логических ошибок (опечатки `Provder`, двойная точка в `super()`, дублирующийся параметр `api_key`, отсутствие `self`, блокирующие запросы в `async`-коде), приведение протокола общения с провайдером к формату `{"role": ..., "content": ...}` и поле `"messages"`, а также реализация корректной иерархии `Provider` → `OpenRouterProvider`, полноценного реестра инструментов и агента с поддержкой tool-calling и fallback-цепочки. **Второе** — создание нового модуля `src/main.py` (точки входа), который читает конфигурацию из переменных окружения и аргументов командной строки, предоставляет интерактивный чат и одноразовый режим запроса, устойчиво переносит ошибки API и корректно завершает работу.

Обе части должны сопровождаться типизацией, docstring-ами, асинхронным HTTP-клиентом с таймаутами и аккуратной обработкой секретов — это делает библиотеку не просто работающим наброском, а основой для дальнейшего развития: подключения реальных инструментов, потокового вывода и расширения набора поддерживаемых провайдеров. Реализация выполняется поэтапно (каркас → `ai.py` → `main` → проверка → тесты → документация), а критерии приёмки из раздела 8 однозначно фиксируют, что именно считается завершённой доработкой.
