# AGENTS.md — BayLang AI

Инструкции для AI-агентов и разработчиков, работающих с проектом **BayLang AI** — Python-библиотекой и CLI-приложением для построения AI-агентов поверх API **OpenRouter** (OpenAI-совместимый chat-completions). Файл описывает архитектуру, контракты ключевых классов, соглашения по коду, известные проблемы и направления доработки. Пользовательская документация (установка, команды, конфигурация) — в [README.md](README.md).

---

## 1. Обзор проекта

Проект состоит из двух модулей: **`src/ai.py`** — переиспользуемое ядро библиотеки (сообщения, контекст, провайдеры, инструменты, агент) и **`src/main.py`** — точка входа с CLI, работой с историями, промптом и логами. Стек: **Python 3.12**, асинхронный HTTP-клиент **httpx**, тесты — **pytest** (пока не написаны), дополнительно используется **python-dotenv** для загрузки `.env`.

Ключевые свойства проекта, которые важно сохранять при доработках: **полностью асинхронное ядро** без блокирующих вызовов, **потоковая отдача сообщений** через асинхронный генератор `Agent.send_with()`, **единая точка форматирования вывода** `format_display()` и **автосохранение истории** сессии. API-ключ живёт только в переменных окружения и никогда не попадает в логи и вывод.

## 3. Архитектура ядра: `src/ai.py`

### 3.1. Иерархия исключений

| Исключение | Назначение |
|---|---|
| `BayLangError` | Базовое исключение библиотеки; от него наследуются все остальные |
| `ConfigurationError` | Отсутствуют или некорректны обязательные параметры (нет ключа, пустое имя инструмента) |
| `ProviderError` | Сбой взаимодействия с LLM-провайдером; атрибуты `status_code` и `body` для диагностики |
| `ToolError` | Ошибка выполнения инструмента; атрибут `tool_name` |

Новые исключения следует добавлять в эту иерархию, чтобы вызывающий код мог ловить их единообразно через `BayLangError`.

### 3.2. Сообщения диалога

Иерархия: `TextMessage` (базовый) → `ToolResultMessage` и `ToolsMessage`. У каждого типа есть константа `MESSAGE_TYPE` (`"text"`, `"tool_result"`, `"tools"`), используемая для диспетчеризации при JSON-сериализации.

- **`TextMessage`** — сообщение с ролью (`user`, `assistant`, `system`, `tool`) и текстом; фабрики `TextMessage.user()`, `.system()`, `.assistant()`, `.tool_result()`. Метод `get_data()` отдаёт формат провайдера `{"role": ..., "content": ...}`, `to_dict()` / `from_dict()` — JSON-сериализацию с полем `type`.
- **`ToolResultMessage`** — результат выполнения инструмента (роль `tool`) с обязательным `tool_id`; при восстановлении из JSON поддерживает и `tool_id`.
- **`ToolsMessage`** — ответ ассистента со списком вызовов инструментов `tools`; поле `tools` сохраняется в JSON всегда, даже если список пуст.

### 3.3. `Context`

Диалоговый контекст с приватным хранилищем сообщений и лимитом `max_messages`. Контракт методов: `add_message` (добавить с авто-trim), `trim` (оставить последние N), `truncate` (оставить первые N — откат при ошибках), `clear`, `last_response` (последний ответ ассистента), `last_messages(count)` (последние N сообщений — для показа при загрузке истории), `get_data` (формат провайдера), `to_dict`/`to_json`/`from_dict`/`from_json` (полная сериализация, tool-цепочки сохраняются), плюс `len()` и итерация по копии списка.

### 3.4. Провайдеры: `Provider` и `OpenRouterProvider`

`Provider` (абстрактный, `abc.ABC`) инкапсулирует HTTP-взаимодействие: переиспользуемый `httpx.AsyncClient`, `post_json()` с обработкой таймаутов и HTTP-ошибок, `parse_response()` с нормализацией ответа в `ProviderResponse` (текст, модель, usage, tool-вызовы), а также `send_stream()` для SSE-стриминга. В `send()` реализован **внутренний цикл повторных попыток**: при любой `ProviderError` запрос повторяется до `fallback_iters` (100) раз с паузой `delay` (5 с).

`OpenRouterProvider` добавляет конкретику OpenRouter: URL `https://openrouter.ai/api/v1/chat/completions`, заголовки `Authorization`, `HTTP-Referer`, `X-Title` и сборку payload (`build_payload`). В payload к **каждому** сообщению и к корню тела запроса добавляется `cache_control: {"type": "ephemeral"}` — подсказка prompt caching для провайдеров, которые его поддерживают. Модель по умолчанию — `openrouter/auto`.

### 3.5. Инструменты: `Tool` и `ToolRegistry`

`Tool` — обёртка над функцией-обработчиком с JSON-схемой параметров в формате OpenAI Function (`get_schema()`). Обработчик может быть синхронным или асинхронным (`execute()` поддерживает оба варианта через `inspect.isawaitable`). `ToolRegistry` хранит инструменты по уникальному имени (`register` бросает `ConfigurationError` при дубликате), отдаёт схемы для запроса (`get_schemas()`) и выполняет вызовы по имени (`execute()`).

### 3.6. Агент: `Agent`

Агент реализует цикл **ReAct**. Основной метод **`send_with()`** — асинхронный генератор: он отправляет контекст провайдеру, добавляет ответ в контекст и отдаёт сообщения вызывающему коду по мере появления — `ToolsMessage` (модель вызывает инструменты), затем `ToolResultMessage` (результат каждого инструмента) и наконец финальный `TextMessage`. Между итерациями цикла с инструментами стоит пауза `asyncio.sleep(self.delay)` (5 с). При ошибке провайдера контекст откатывается через `truncate`, при исчерпании `max_iters` бросается `ProviderError`.

Метод `send()` — обёртка над генератором, возвращает только финальный текст ответа. Также есть `reset()` (очистка контекста и `last_response`) и `disconnect()` (закрытие HTTP-соединений провайдера — вызывать в `finally`).

## 4. Точка входа: `src/main.py`

Модуль организован блоками: **форматирование вывода** (`format_display`, `ROLE_LABELS`), **домашняя папка и истории** (`ensure_app_dirs`, `load_system_prompt`, `save_history`, `autosave_history`, `load_history`, `list_histories`, `print_histories`, `print_last_messages`), **аргументы CLI** (`parse_args`, `get_show_messages`, `mask_api_key`), **сборка агента** (`build_agent`) и **режимы работы** (`run_interactive`, `run_app`, `main`). Настройка логирования — `setup_logging()`.

Ключевые контракты:

- **`format_display(message) -> str`** — единственная точка форматирования всех сообщений для пользователя: текст модели и реплики выводятся с меткой роли (`you`, `assistant`, `system`), результаты инструментов — как `tool[<id>] > ...`, вызовы инструментов — многострочно с аргументами и id. Любое изменение формата вывода делается **только здесь**.
- **История сессии** сохраняется автоматически: `autosave_history()` вызывается после каждого ответа модели и повторно в `finally` у `run_app()`. Имя файла — метка времени сессии (unix), формат — JSON pretty через `Context.to_json(indent=2)`. Сбой автосохранения не прерывает диалог (логируется предупреждение).
- **Показ последних сообщений** при загрузке истории выполняет `print_last_messages()`: она пропускает `ToolResultMessage` и системные сообщения, количество настраивается флагом `--show-messages` или переменной `BAYLANG_SHOW_MESSAGES` (приоритет: аргумент → env → 10).
- **Логи**: `RotatingFileHandler` на `~/.baylang/logs/baylang.log` (1 МБ × 5 бэкапов), уровень `INFO` в файл и `WARNING` в консоль, при `--verbose` — `DEBUG` везде. Диагностические сообщения идут в `logging`, пользовательский вывод — через `print`.
- **Вывод из генератора**: `run_interactive()` итерирует `agent.send_with()` и печатает каждое сообщение через `format_display()` — текст, вызовы инструментов и результаты видны пользователю по мере появления.

## 7. Соглашения по коду

- **Стиль и типы**: Python 3.12, `from __future__ import annotations`, аннотации типов везде, dataclass-ы там, где уместно (`ProviderResponse`).
- **Докстроки**: Google-style **на русском языке** — краткое описание, затем `Args`, `Returns`, `Raises`; докстринги модулей документируют назначение и контракты целиком.
- **Экспорт**: каждый модуль ведёт `__all__` с публичным API; приватные функции помечаются подчёркиванием (например, `_normalize_history_name`).
- **Асинхронность**: только `httpx.AsyncClient`; блокирующие вызовы (чтение файлов допустимо, сеть — нет) в async-коде не использовать; длинные цепочки — через `async for` и генераторы (`send_with`).
- **Ошибки**: пользовательские сообщения об ошибках — на русском, понятные и с подсказкой действия; исключения — из иерархии `BayLangError`; аварии вспомогательных операций (например, автосохранение) не должны ронять приложение.
- **Логирование**: `logger = logging.getLogger(__name__)`; диагностика и тайминги — в логи, пользовательский вывод — через `print` и `format_display`.
- **Безопасность**: API-ключ только из переменных окружения, выводить в логи лишь маску (`mask_api_key`), файл `.env` никогда не коммитить и не включать в артефакты сборки; `.gitignore` содержит `.env`, `.dockerignore` — исключает лишнее из контекста сборки.
- **Документация**: при изменении CLI, переменных окружения, формата данных или Docker-обвязки синхронно обновлять README.md и этот файл; новые известные проблемы фиксировать в разделе 8.

## 8. Известные проблемы и ограничения

1. **Импорты и точка входа** — `src/main.py` делает `from ai import ...`, поэтому надёжный запуск — `python src/main.py` (или из каталога `src/`); `python -m src.main` из корня падает с `ModuleNotFoundError`, так как `src/ai.py` не виден как топ-level модуль `ai`. Файлов `src/__init__.py` и `src/__main__.py` нет (старый README их ошибочно упоминал); стоит нормализовать пакет и единообразить импорты (`from src.ai import ...` против `from ai import ...`).
2. **Неописанные в коде фичи из старого README и докстринга `main.py`** — одноразовый режим `--prompt` и флаги `--prompt-file`, `--no-tools`, `--save`, а также демо-инструменты `get_current_time`/`web_search` и fallback-провайдер с `send_with_fallback` **не реализованы** (в `parse_args` этих аргументов нет, `build_agent` регистрирует пустой `ToolRegistry`). Докстринги нужно привести в соответствие с кодом либо вернуть эти возможности.
3. **`build.sh run` ограничен** — контейнер запускается без `-it`, а аргументы, переданные после тега, подменяют `CMD ["bash"]` (у образа нет `ENTRYPOINT`), поэтому передать их приложению через `./build.sh run` нельзя — работает только прямой `docker run ... python src/main.py`. Также `IMAGE_NAME`/`IMAGE_TAG` захардкожены (`bayrell/baylang-ai-command:1.0.0`) вопреки комментарию о переменных окружения.
4. **Prompt caching: расхождение кода и докстринга** — `build_payload` добавляет `cache_control` к каждому сообщению и к корню payload, тогда как докстринг говорит о последнем сообщении. Уточнить документацию или сузить подсказку до префикса диалога.
5. **Повторные попытки провайдера** — `Provider.send` молча повторяет запрос до 100 раз с паузой 5 с при любой `ProviderError` (включая 401 и 400, где повтор бессмыслен); стоит разделять транзиентные и перманентные ошибки и ограничить число попыток. Также `Provider.post_json` вызывает `self.build_headers()`, который определён только в `OpenRouterProvider`, — наследники `Provider` обязаны его реализовывать, это стоит закрепить абстрактным методом.
6. **Пауза 5 с между итерациями инструментов** — `Agent.send_with` ждёт `asyncio.sleep(self.delay)` после каждого tool-цикла; для интерактивного диалога это заметные задержки, значение стоит сделать настраиваемым и уменьшить по умолчанию.

## Итог

**BayLang AI** устроен просто и предсказуемо: ядро (`src/ai.py`) отвечает за сообщения, контекст, провайдеры, инструменты и ReAct-агента с генератором `send_with()`, а точка входа (`src/main.py`) — за CLI, `format_display`, истории в `~/.baylang/history/`, промпт в `~/.baylang/prompt.txt` и логи с ротацией. При доработках сохраняйте асинхронность ядра, единую точку форматирования вывода, автосохранение историй и правило безопасности: **API-ключ только из окружения, маска в логах, `.env` никогда не коммитится**.
